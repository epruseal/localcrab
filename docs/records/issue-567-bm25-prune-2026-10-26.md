## 8. #542 하네스 S2 대조 (새 질의 종류 포함)

- 코퍼스: 이 브랜치의 생성기로 `generate --preset S2 --seed 542`. 질의는 48개다(기존 42개와 `common-heavy` 셋, `common-only` 셋). 기존 질의와 문서 본문은 기존 생성기의 S2와 같다(새 질의는 마지막에 계획한다). 흔한 단어 셋의 문서 비율은 Zipf 1위 0.999, 2위 0.985, 12위 0.574였다. 흔한 단어 여섯은 0.999에서 0.807 사이였다.
- 적재는 head 하네스로 한 번 했다(`load: COMPLETE`, 336.89초). base(`origin/main`의 분리 checkout)와 head의 `run`(기본 설정)을 같은 적재 디렉터리에서 순차로 돌렸다. 실행 조건은 1절과 같다.
- 판정: 두 보고서 모두 `COMPLETE`, `bm25_index`는 `db`다. 분류는 두 쪽 모두 BM25, FTS, vector가 pass 48, 결합이 pass 47과 miss 1(`long-tail-1`, 기존 한계)이다. 자동 선택 오류 0, 반복 결함 표지(누출, 중복, 범위 오류, 경고 누락, 조용한 부분 결과, 동시 쓰기 누출과 중복)는 두 쪽 모두 0이다. `compare` 출력은 `COMPARE: CLEAN`이었다.
- 지연 요구치(p95, ms, base / head / 요구): BM25 레그 5617.6 / 165.5 / 500, 명시 단일 팩 요청 4610.7 / 311.3 / 800, 전체 범위 요청 8322.1 / 953.6 / 2000, 자동 선택 요청 7119.2 / 985.2 / 2500, 동시 쓰기 중 명시 단일 10089.0 / 801.2 / 1600, 동시 쓰기 중 전체 범위 17672.7 / 2459.0 / 4000, 동시 쓰기 중 자동 선택 15386.8 / 2409.3 / 5000. base는 일곱 항목 모두 요구치를 넘었고 head는 모두 요구치 안이었다. FTS 레그와 vector 레그, 명시 다중 팩 요청은 두 쪽 모두 요구치 안이었다.
- 같은 적재 디렉터리의 사본에서 새 질의의 BM25 레그(서비스 요청 크기, 3회)를 따로 쟀다(ms, base / head): `common-heavy` 명시 단일 4337.7 / 152.2, 전체 범위 5455.6 / 170.5, 자동 선택 팩별 탐침 5483.7 / 509.8, `common-only` 명시 단일 셋 4358.2 / 156.4, 전체 범위 셋 5692.1 / 166.0, 전체 범위 여섯(잔여 형태) 7838.7 / 739.9.
- 자원(base / head): 측정 프로세스 최대 RSS 352796672 / 342999040 bytes, 동시 쓰기 지연 p95 318.3 / 373.5ms(요구 500), 잠금 대기 p95 0.4 / 1.6ms, `fts_index_ratio` 1.7 / 1.7, 노드 색인 바이트와 `search_index_ratio_all`은 같았다. 쓰기 경로는 바꾸지 않았다. 동시 쓰기 지연의 차이는 같은 60초 동안 head가 질의를 더 많이 돌린 결과로 보이지만 따로 재지 않았다.
- 첫 시도: 처음에는 두 종류 모두 Zipf 상위 여섯 단어를 썼다. 그 코퍼스에서 head의 새 질의 BM25 레그는 여섯 개 모두 500ms를 넘었다(678.1에서 1292.9ms). 상위 여섯 단어는 모두 거의 모든 문서에 있어 잔여 1과 같은 꼴이다. 그래서 라이브의 통과 형태(거의 모든 문서에 있는 용어와 문서 일부에만 있는 용어 하나)를 따른 셋 조합으로 바꾸고, 상위 여섯만으로 된 질의는 잔여 형태 하나로 남겼다.
