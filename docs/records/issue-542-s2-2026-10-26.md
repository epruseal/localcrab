# #542 S2 측정 기록 (2026-10-26)

이 기록은 2026-10-26에 관측한 값이다. 갱신하지 않는다. 판정 기준과 재현 명령은 `docs/issue-542-search-baseline.md`에 있다. 다음 측정은 새 날짜의 기록으로 남긴다.

## 1. 조건

- 코드: 이 기록을 더한 브랜치의 부모 커밋(`origin/main`, #541, #550, #556 포함). 하네스와 제품 코드는 바꾸지 않았다.

- 실행: 생성, 적재, 측정, probe와 선행 점검을 transient systemd 서비스(`CPUQuota=100%`, `Nice=19`, `IOSchedulingClass=best-effort`, `IOSchedulingPriority=7`, `LimitAS=2G`, `MALLOC_ARENA_MAX=2`, `PYTHONDONTWRITEBYTECODE=1`, `TMPDIR`은 디스크 경로)로 하나씩 돌렸다. 생성 둘, 적재, 기본 실행, 축소 상한 실행, backfill probe, 보조 실행의 일곱 단계는 실행 중 주 PID에서 주소 공간 상한 2GiB, cgroup `cpu.max` `100000 100000`, nice 19, best-effort 7을 확인해 파일로 남겼다. 선행 점검 둘은 결과 출력만 남았다. 측정 보고서 `environment`에도 같은 주소 공간 상한과 `cpu.max`가 남았다. Python 3.13.5, SQLite 3.46.1.
- 서비스 시간 상한: S1 적재는 #556 기록의 72.6초다. S1 실행 소요는 날짜 기록에 없다. 그래서 #556 측정 때 남은 작업자 단계 로그의 시작 시각 차이(실행 하나당 약 76초)를 썼다. 노드 비율 3.03을 곱한 추정은 적재 약 220초, 실행 약 230초였다. 작업자 기록에 따르면 `RuntimeMaxSec`은 생성 900초, 적재와 실행과 probe 각 1800초, 선행 점검의 selftest 600초와 S0 시험 1200초였다. 이 인자는 서비스 로그에 남지 않았다. 하네스 자체의 시간 예산(설계 9.2절, S2 60분)도 함께 걸렸다.

## 11. 보조 관측 (판정 밖)

아래 둘은 설계 3절의 S2 판정에 들지 않는다. 라이브 적용 절차(#541 12절)의 backfill 단계와 rollback 경로를 S2 규모에서 보려고 같은 적재 디렉터리의 사본으로 따로 돌렸다. 적재 디렉터리는 바꾸지 않았다.

### 11.1 적재된 사본의 색인 제거와 backfill

- 방법: 적재 디렉터리의 `doc.db` 사본에서 저장소 API로 `node_bm25_drop`을 부르고 다시 열어 상태 `backfill`을 확인했다. 그 뒤 `node_bm25_backfill_step(500)`을 상태가 `ready`가 될 때까지 부르고, pending을 소진하고, `node_bm25_verify`를 불렀다. CLI `opencrab packs bm25-index backfill`과 `verify`가 부르는 저장소 메서드와 같다.
- 결과: backfill은 124단계, 21.9초에 61100행을 처리했다. 단계 하나의 최장 시간은 0.27초였다. 소진 뒤 pending은 0이었다. `verify`는 75.9초 걸렸고 `ok: true`, `missing` 0, `orphans` 0, `mismatched_meta` 0, `mismatched_terms` 0, `stats_ok` true였다. 프로세스 peak RSS는 94.9MiB였다.
- 다시 만든 노드 색인은 42.8MiB였다. 적재 때 쓰기 동기화로 만든 색인(43.2MiB)과 거의 같다.

### 11.2 킬 스위치 경로 (`OPENCRAB_BM25_DB_INDEX=0`, 기본 설정)

- 방법: 같은 적재 디렉터리로 하네스 `run`을 기본 설정과 환경 변수 `OPENCRAB_BM25_DB_INDEX=0`으로 한 번 돌렸다. 보고서 `bm25_index`는 `memory`였다. 이 경로는 상태 `backfill` 동안과 검색 rollback(#541 5.5절) 때 서비스가 쓰는 기존 메모리 창 경로다.
- 실행 판정: `COMPLETE`. 반복 결함 표지(누출, 중복, 범위 오류, 경고 누락, 조용한 부분 결과, 동시 쓰기 누출과 중복)는 모두 0이다.
- 품질: BM25 pass 35, partial_flagged 7. 결합 pass 37, partial_flagged 4, miss 1(`long-tail-1`). 질의 39개의 BM25 레그에 `BM25 coverage partial rows` 경고가 붙었다. 창(행 상한 50000)이 61100행을 모두 담지 못하기 때문이다. 놓친 정답은 모두 경고와 함께 나왔다.
- 지연: cold 첫 요청 12.7초(그 가운데 BM25 첫 구축 11.9초, 요구 15초). BM25 레그 p95 952.4ms(요구 500ms), 명시 단일 팩 요청 p95 878.9ms(요구 800ms). 동시 쓰기 중 명시 단일 팩 p95 2718.5ms(요구 1600ms), 전체 범위 p95 4808.2ms(요구 4000ms)였다.
- freshness: BM25의 새 문서 반영 15.8초(요구 10초). 수정은 30초 안에 반영되지 않았고(`not_converged`), 삭제는 수정이 반영되지 않아 선행 조건이 성립하지 않았다(`precondition_failed`). FTS와 vector는 요구치 안이다.
- 자원: peak RSS 543.6MiB, 동시 쓰기 지연 p95 880.1ms(요구 500ms), 잠금 대기 p95 209.8ms.
