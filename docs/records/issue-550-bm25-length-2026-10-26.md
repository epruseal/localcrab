# #550 BM25 긴 문서 과벌점 측정 기록 (2026-10-26)

이 기록은 2026-10-26에 관측한 값이다. 갱신하지 않는다. 설계와 판정 근거는 `docs/issue-550-bm25-length.md`에 있다.

## 1. 착수 전 probe: 길이 정의와 점수 식 후보

- 입력: `scripts/search_corpus.py generate --preset S1 --seed 542`를 base(`origin/main`, #541과 #542 장애 주입 하네스 포함)의 `scripts/search_baseline.py load`로 적재한 `doc_nodes` 20150행. 적재는 `COMPLETE`였다.
- 실행: transient systemd 서비스(`CPUQuota=100%`, `Nice=19`, `IOSchedulingClass=best-effort`, `IOSchedulingPriority=7`, `LimitAS=2G`, `MALLOC_ARENA_MAX=2`, `PYTHONDONTWRITEBYTECODE=1`). 8GB RAM, 4코어 aarch64, Python 3.13.5, SQLite 3.46.1. 한 번에 하나씩 돌렸다.
- 방법: 읽기 전용 연결로 `doc_nodes` 전량을 읽어 `tokenize(_node_text(node)[:65536])`를 만들고, 질의 42개마다 요청 팩(명시 팩과 주체 A 읽기 범위의 교집합, 미지정이면 읽기 범위)과 `spaces` 안에서 전체 점수 목록을 계산했다. 자동 선택은 흉내 내지 않고 읽기 범위 전체로 계산했다.

평균 길이는 n-gram 포함 토큰으로 251.6, 공백 단어로 115.5였다. `top-k-pressure-1` 정답의 길이는 n-gram 포함 722(평균의 2.87배), 공백 단어 320(2.77배)이었다.

| 후보 | `top-k-pressure-1` 정답 순위(41건 중) | 상위 10 순서가 바뀐 질의(대상 제외) |
|---|---|---|
| 현행 | 41 | 해당 없음 |
| 길이를 공백 단어 수로 | 41 | 9개(`explicit-multi-0`, `whole-scope-0`, `whole-scope-2`, `duplicate-body-2`, `top-k-pressure-0`, `top-k-pressure-2`, `auto-title` 셋) |
| `b = 0.5` | 41 | 0개 |
| `b = 0.3` | 38 | 0개 |
| BM25+ `δ = 0.5` | 9 | 0개 |
| BM25+ `δ = 1.0` | 1 | 0개(전체 목록 순서는 `auto-title` 셋이 바뀜) |

BM25+ `δ = 1.0`에서 `top-k-pressure-1`의 점수는 정답 23.3884, 가장 높은 대조군 19.8203이었다. 현행 식에서는 가장 높은 대조군 13.6588이 1위였다. 모든 후보에서 점수가 0보다 큰 문서 집합은 현행과 같았다.

## 2. 착수 전 probe: 하네스 판정과 결합 경로

- 방법: 같은 적재 디렉터리로 #542 하네스 `run`(기본 설정, `--repeats 1`)을 세 번 돌렸다. 하네스 프로세스 안에서만 점수 함수를 바꾸는 시험용 래퍼를 썼고 저장소 파일은 바꾸지 않았다. 변형은 현행, BM25 레그만 BM25+, BM25 레그와 reranker 교차 점수 모두 BM25+다.
- 결과: 세 보고서 모두 `COMPLETE`. 질의별 레그 분류와 자동 선택 판정이 바뀐 질의는 `top-k-pressure-1` 하나였다. 이 질의의 BM25 레그는 현행 `partial_silent`(정답 41위, 대조군 40개 위)에서 두 BM25+ 변형 모두 `pass`(대조군 0개 위)가 됐다. 결합은 세 변형 모두 `partial_silent`(대조군 10개 위)였다.
- 결합 진단: BM25+ 변형의 실행 사본으로 `HybridQuery.query`의 rerank 입력을 기록했다. vector 40건(대조군 9), BM25 41건(정답 1위, 대조군 40), FTS 8건(대조군 8)이었다. rerank 결과 72건 가운데 정답은 39위였다. 출력한 상위 15건은 모두 대조군이었고, 그 가운데 상위 14건은 각각 둘이나 세 레그에 나왔다.
- 질의 42개 전체 대조: 같은 실행 사본 두 벌(측정 전용 팩의 freshness와 동시 쓰기가 남은 상태)에서 현행과 BM25+로 자동 선택, BM25 레그(`_profile_for_query`의 요청 크기, limit 10에서 60), rerank 결합, 평면 병합(`use_rerank=False`)의 id 목록을 얻었다. 자동 선택과 rerank 결합은 42개 모두 같았다. BM25 레그는 `top-k-pressure-1`만 달랐다. 평면 병합은 여섯 질의가 달랐다.

## 3. 구현 뒤 전체 스위트 대사

- 코드: base는 `origin/main`(이 브랜치의 분기점), head는 이 브랜치의 구현 커밋. base는 별도 detached worktree에서 돌렸다.
- 실행: `docs/gate-recipes.md` 6절의 재현 명령을 위 transient 서비스 안에서 base, head 순으로 하나씩 돌렸다. 실행 중 주 PID에서 주소 공간 상한 2147483648바이트와 cgroup `cpu.max` `100000 100000`을 확인했다. `OPENCRAB_PG_TEST_URL`은 두 실행 모두 두지 않았다. 공유 PostgreSQL 컨테이너를 쓰지 않기 위해서이며, 두 실행이 같은 PG 시험을 똑같이 건너뛴다.
- 결과: 두 요약 모두 `VERDICT:COMPLETE`. base는 tests 8864, skipped 508, 실패 6이다. head는 tests 8875, skipped 508, 실패 6이다. 실패 id 집합은 같다(`tests/test_issue80_sql_graph.py`의 PG와 Neo4j 런타임 시험 여섯 개. 두 실행 모두 서비스에 접속하기 전에 필수 환경 변수 누락으로 실패했다. PG 시험 넷은 `OPENCRAB_PG_TEST_URL`과 `OPENCRAB_ISSUE80_SERVICE_APPLY`, Neo4j 시험 둘은 Neo4j 접속 변수와 `OPENCRAB_ISSUE80_SERVICE_APPLY`가 없었다). 상태 대조에서 바뀐 항목은 `tests/test_bm25_lower_bound.py`의 새 시험 11개 추가(모두 pass)뿐이다. 상태가 바뀐 기존 시험과 사라진 시험은 없다.
- 역변이: 폐기용 checkout에서 `_DELTA`를 0.0(옛 식과 같은 값)으로 바꾸자 `tests/test_bm25_lower_bound.py`의 시험 다섯 개(긴 문서 시험 둘, 하한 시험, 동점 경계 시험 둘)가 실패했다. 되돌린 뒤 전부 통과했다.
- CI 기본 환경: 사용자 이름을 별도로 두고 기본 basetemp(시스템 임시 디렉터리)로 바꾼 네 시험 파일(`test_bm25_lower_bound.py`, `test_bm25_memory_bounds.py`, `test_bm25_pack_buckets.py`, `test_node_bm25_index.py`)을 돌려 전부 통과했다.

## 4. 구현 뒤 #542 하네스 대조 (base와 head)

- 입력: 1절과 같은 코퍼스 한 벌. 적재는 checkout마다 따로 했고 둘 다 `COMPLETE`였다(base 73.0초, head 72.3초).
- 실행: base 적재, base 기본, base 축소 상한, head 적재, head 기본, head 축소 상한을 하나씩 돌렸다. 네 보고서 모두 `verdict: COMPLETE`, `bm25_index`는 `db`, `environment`에 주소 공간 상한 2GiB와 `cpu.max` `100000 100000`이 남았다.

| 레그 | base 기본 | head 기본 | base 축소 상한 | head 축소 상한 |
|---|---|---|---|---|
| BM25 | pass 41, partial_silent 1 | pass 42 | pass 41, partial_silent 1 | pass 42 |
| FTS | pass 42 | pass 42 | pass 42 | pass 42 |
| vector | pass 42 | pass 42 | pass 42 | pass 42 |
| 결합 | pass 40, partial_silent 1, miss 1 | 같음 | pass 40, partial_silent 1, miss 1 | 같음 |
| 자동 선택 오류 | 0 | 0 | 0 | 0 |

- 질의별 대조: 두 설정 모두 분류나 정답 순위가 바뀐 질의는 `top-k-pressure-1` 하나다. BM25는 `partial_silent`(정답 41위, 대조군 40개 위)에서 `pass`(대조군 0개 위)가 됐다. 결합은 base와 같은 `partial_silent`(대조군 10개 위)다. `whole-scope` 셋의 `effective` 값 차이는 적재마다 무작위로 정해지는 주체 기본 팩 ID뿐이다(#542 설계 8.2절).
- 반복 결함 표지: 누출, 중복, 범위 오류, 경고 누락, 동시 쓰기 누출과 중복은 네 보고서 모두 0이다. 조용한 부분 결과 표지는 base 10(BM25와 결합, 다섯 반복), head 5(결합만)다.
- 요구치: base에서 미충족이던 `quality_leg_non_pass`가 head에서 충족됐다. `quality_combined_non_pass`와 `quality_partial_silent`는 양쪽 모두 미충족이다.
- `compare` 출력(두 설정 같음): `REGRESSION head repeat defect partial_silent: 5`, `REGRESSION top-k-pressure-1:combined: partial_silent`, 종료 코드 1. 두 줄 모두 base에도 있던 결합의 `partial_silent`다. `compare`는 head의 `partial_silent`를 base와 무관하게 회귀로 센다. 원인은 설계 8절이다.
- 지연, freshness, 자원: 요청 p95(명시 단일 팩, 명시 다중, 전체 범위, 자동 선택)는 기본 설정에서 base 145.7, 11.4, 19.0, 13.1ms, head 144.9, 10.4, 18.4, 13.2ms였다. BM25 레그 p95는 네 실행 모두 2.7ms, cold 첫 요청은 21.2ms에서 22.8ms 사이였다. freshness의 BM25 반영은 모두 0.001초 이하였다. 표본 peak RSS는 146.6MiB에서 152.6MiB 사이였다.

## 5. 구현 뒤 평면 병합과 결합 대조

- 방법: base 기본 실행 디렉터리의 사본 두 벌에서 base checkout과 head checkout이 각각 질의 42개의 자동 선택, BM25 레그(`_profile_for_query`의 요청 크기, limit 10에서 60), rerank 결합, 평면 병합(`use_rerank=False`)의 id 목록을 냈다. 각 프로세스가 자기 checkout의 `opencrab`을 import했음을 출력으로 확인했다.
- 결과: 자동 선택의 `effective`와 rerank 결합은 42개 모두 같다. BM25 id 목록은 `top-k-pressure-1`만 다르다. BM25 결과가 있는 질의 36개는 모두 점수 값이 다르다. 결과가 없는 `explicit-forbidden`과 `long-tail`의 여섯 질의는 양쪽 모두 빈 목록이다. 평면 병합이 바뀐 질의는 2절의 표와 같은 여섯 개이고 정답 순위도 2절의 표와 같다. 정답 순위가 내려간 질의는 없다.
