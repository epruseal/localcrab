# #667 흔한 용어 질의의 BM25 지연: 측정 기록 (2026-11-18)

설계는 `docs/issue-667-bm25-posting-cache.md`다. 이 기록은 설계가 인용하는 측정을 날짜와 함께 남긴다. 수치는 그날의 관측이다. 기준으로 쓰지 않는다. 라이브 데이터는 읽지 않았다. 모든 값은 합성 코퍼스(`scripts/search_corpus.py`, 프리셋 S3, 시드 542)에서 나왔다.

## 1. 결론

- 선택: 선택지 3(프로세스 안 캐시)을 구현했다. 파일별 `PRAGMA data_version` 표지와 읽기 전후 비교로 무효화하고 흔한 용어의 통계(df, cf)와 출현 목록 배열을 캐시한다. 색인 형식을 바꾸지 않으므로 라이브 재색인이 필요 없다.
- 선택지 4(경고 기준)는 별도 커밋으로 넣었다. 질의 비용이 df와 cf 둘에 걸리므로 `cf > FULL_SCAN_CF_MAX`인 용어도 흔한 용어로 센다. 이 기준으로 예산을 넘은 놓친 경고를 실측하지는 못했다. 근거는 3.3절의 비용 모델이다.
- 선택지 1(영향도 순서 표)과 2(블록 최대값)는 색인 형식 변경이라 설계와 측정에서 멈췄다. 블록 최대값은 현실적인 블록 크기에서 건너뛰기가 거의 없다(3.2절). 선택지 5(근사)는 채택하지 않았다.
- Rust(PyO3) 이식은 채택하지 않았다. 질의 시간의 85.6%가 SQLite C 안이고 Python 바이트코드는 3.8%다(2절).
- 한계: 쓰기가 이어지는 구간에서는 세대가 매번 바뀌어 이득이 없다(4절 쓰기 사이 측정). 쓰기가 드문 구간에서 흔한 용어 질의의 웜 시간이 줄어든다. 쓰기와 무관하게 줄이려면 색인 형식 변경(선택지 1, 2)과 라이브 재색인 비용 측정이 필요하다. 이 이슈의 후속으로 남긴다.

## 2. 프로파일: Python 바이트코드 대 SQLite C (2026-11-18 11:35, 구현 전 코드)

- 대상: 합성 S3 사본(노드 120000)의 흔한 용어 여섯 단어(질의 용어 열 개), 전체 범위, `limit` 10, 웜 약 1285ms. 합성 하네스에서 이 질의의 BM25 레그 경고가 나는 유일한 형태다.
- 도구: `py-spy`가 이 장치에 없고 외부 통신을 하지 않아 설치할 수 없었다. 대신 두 방법으로 교차 검증했다. 하나는 같은 프로세스의 샘플링 스레드로 질의를 돌리는 스레드의 호출 스택을 0.3ms 간격으로 읽는 방법이다. 다른 하나는 `cProfile`이다. SQLite 실행 중에는 GIL이 풀리므로 샘플러가 그 구간을 정확히 본다.
- 분류: SQLite C는 커서 실행과 순회 줄이다. numpy C는 `np.fromstring` 줄과 numpy 내부 함수다. Python은 그 밖의 바이트코드이며 numpy 연산자 식을 포함한다.

샘플 비율(14494개 샘플, 같은 질의 네 번):

| 함수 묶음 | SQLite C | numpy C | Python | 합계 |
|---|---|---|---|---|
| `_postings`(출현 목록 스캔과 문자열 해석) | 55.3% | 8.3% | 0.5% | 64.2% |
| `search`의 df와 cf 조회(`fts5vocab` row) | 21.7% | 0 | 0 | 21.7% |
| `_match_docs` | 7.5% | 0.6% | 0 | 8.1% |
| 점수 합산(`add_tf`, `_contrib`, `keep`, `_kth` 등) | 0 | 1.7% | 2.7% | 4.4% |
| 다시 토큰화(`retokenise`, `tokenize`) | 1.0% | 0 | 0 | 1.0% |
| 기타 | 0.1% | 0 | 0.5% | 0.6% |
| 전체 | 85.6% | 10.6% | 3.8% | 100% |

`cProfile`(세 번 합산, 프로파일 오버헤드 포함)의 대응값: SQLite 실행과 순회가 전체의 약 82%, `np.fromstring`이 약 7%, 나머지 Python과 numpy가 약 11%다. 두 방법의 순서가 같다.

Rust(PyO3) 이식 효용 판단: Python 바이트코드는 한 자릿수 비율이고 numpy C까지 합쳐도 약 14%다. 이 부분을 Rust로 완전히 옮기고 0으로 만들어도 질의 시간은 약 14% 줄 뿐이다. 나머지는 SQLite 안이다. Rust가 SQLite 접근을 그대로 쓰면 이 시간은 줄지 않는다. 줄이는 수단은 FTS5 내부 세그먼트를 직접 읽는 것인데, 비공개 형식과 삭제 표지를 재구현해야 한다. 그래서 채택하지 않았다.

## 3. 선택지 측정

### 3.1 용어별 비용 (같은 질의, 열 용어, 2026-11-18 11:35)

| 읽기 | 용어당 시간 | 규모와의 관계 |
|---|---|---|
| `fts5vocab` instance 표 스캔(`_postings`) | 91~1036ms | cf에 비례한다. 용어의 cf는 약 25만에서 367만이다 |
| `fts5vocab` row 조회(df, cf) | 20~49ms | 용어 열 개에 합계 약 280ms |
| `MATCH`와 `docs` 조인(`_match_docs`) | 98~118ms | df에 완만히 비례한다 |
| `MATCH` 행 수만 | 18~26ms | |
| `docs` 열 전체를 읽어 배열로 만들기 | 183ms(문서 120000) | 세대마다 한 번이므로 설계는 이 캐시를 만들지 않는다 |

`_postings`가 내는 두 배열이 모두 int64이므로 출현 목록 하나(두 배열 한 쌍)는 문서 하나에 16바이트다. 문서 약 12만에 모두 나오는 용어 하나가 약 1.9MB다.

### 3.2 선택지 2: 블록 최대값의 시뮬레이션 (최선 경우)

같은 질의에서 문서를 `doc_key` 순서로 블록으로 묶고, 블록마다 용어별 최대 기여의 합이 최종 k번째 점수(θ) 이상인 블록 수를 셌다. θ를 처음부터 아는 최선 경우다. 실제 가지치기는 θ가 점점 오르므로 이보다 못하다.

| 블록 크기 | θ 이상 블록 비율 | 살펴볼 문서(전체 120000) |
|---|---|---|
| 32 | 26.9% | 약 32000 |
| 64 | 62.7% | 약 75000 |
| 128 | 94.0% | 약 113000 |
| 256 | 99.8% | 약 120000 |
| 512 이상 | 100% | 전량 |

흔한 용어는 `tf`가 커서 기여가 상한(`k1 + 1`)에 가까이 포화한다. k번째 점수(약 3.29)가 모든 용어의 상한 합(약 3.70)과 실제 최대(약 3.32)에 모두 붙어 있다. 128 이상의 블록에서는 거의 모든 블록이 θ를 넘을 수 있다. 32까지 줄이면 최선 경우에 약 3.7배 줄지만 용어마다 `doc_key` 블록 최대값 저장 구조와 건너뛰기용 문서 순서 출현 목록(FTS5가 내주지 않는 구조)이 필요하다. 이는 색인 형식 변경이며 라이브 재색인이 필요하다. 이 경우 설계와 측정에서 멈추고 채택하지 않는다.

### 3.3 선택지 4: 경고 기준 (합성 질의 형태 비교)

질의 시간은 df와 cf 둘에 걸린다. 같은 장치에서 흔한 용어 없이 cf가 큰 용어만으로 질의를 만들어 쟀다(df가 문서의 절반 이하인 용어만, 전체 범위).

| 질의 | df 합 | cf 합 | 시간(ms) | 지금 기준: 흔한 용어로 셈 | 새 기준: 흔한 용어로 셈 |
|---|---|---|---|---|---|
| 큰 용어 하나 | 56251 | 87128 | 117 | 아니오 | 예 |
| 큰 용어 셋 | 154933 | 231177 | 270 | 아니오 | 예 |
| 큰 용어 여섯 | 277894 | 398491 | 486 | 아니오 | 예 |
| 매우 흔한 용어 하나 | 118070 | 854568 | 422 | 예 | 예 |
| 매우 흔한 용어 둘 | 225926 | 1253418 | 590 | 예 | 예 |

"지금 기준"은 `2*df > 색인 문서 수`다. "새 기준"은 이 식 또는 `cf > 50000`이다. 경고는 시간이 예산 500ms를 넘고 흔한 용어가 있을 때만 붙는다. 이 표에서 예산을 넘은 질의는 마지막 줄뿐이다. 큰 용어 여섯 단어의 질의는 486ms로 예산 바로 아래이며, 용어가 하나 더 늘거나 코퍼스가 더 크면 예산을 넘는데 지금 기준은 그때도 경고를 붙이지 않는다. (큰 용어는 df가 문서의 절반 이하인 용어 가운데 cf가 큰 순으로 골랐다. 질의를 한 용어씩 늘린 cf 합의 차이로 보면 가장 작은 용어의 cf도 50000을 넘는다.)

df 합이 비슷해도 시간은 cf에 따라 두세 배 다르다. cf만으로는 df가 큰 용어를 놓친다. 그래서 둘 가운데 하나만 커도 흔한 용어로 세는 기준을 택한다.

### 3.4 선택지 3: 스크래치 시제품 (구현 전, 2026-11-18 11:37)

저장소 밖 스크래치 스크립트로 `_postings`와 `_match_docs`를 무효화 없는 사전 캐시로 바꾸어 같은 사본에서 쟀다. 한 프로세스에서 같은 질의를 네 번 돌려 첫 번째와 웜(나머지 중앙값)을 적는다. 결과 목록의 해시는 구현 전 코드의 해시와 모두 같았다.

| 질의(형태) | 구현 전 웜(ms) | 출현 목록만 캐시, 웜(ms) | 출현 목록과 docs 열 캐시, 웜(ms) |
|---|---|---|---|
| 흔한 용어 여섯 단어, 전체 범위 | 1291 | 462 | 399 |
| 흔한 용어 세 단어, 전체 범위 | 298 | 250 | 208 |
| 흔한 용어 세 단어, 자동 선택 탐침 | 748 | 696 | 638 |

시제품은 용어 통계(df, cf) 조회를 캐시하지 않았다. 그 상태에서 시제품의 `cProfile`은 남은 시간의 대부분이 `fts5vocab` row 조회(여섯 단어 질의의 질의당 약 260ms)임을 보였다. 설계는 이 조회도 캐시한다. 그 효과는 시제품에 없고 프로파일에서 예측한 값이다. 구현 뒤 측정(4절)이 첫 증거다.

세 번째 열(`docs` 열 캐시를 더함)은 두 번째 열보다 여섯 단어 형태에서 약 60ms 낮다. 이 캐시는 세대마다 `docs` 표 전체를 읽는 비용(3.1절)을 지고 쓰기 사이마다 다시 만들어야 한다. 이득이 작고 쓰기 구간의 회귀 위험이 있어 설계에서 뺐다. 자동 선택 탐침 형태의 이득은 작다(748ms에서 696ms, 출현 목록만 캐시한 경우).

### 3.5 `PRAGMA data_version`의 의미 (2026-11-18, 합성 DB, WAL 모드)

스크래치 스크립트로 다음을 재었다. 표지 연결은 읽기만 한다.

| 상황 | 표지 연결의 값 |
|---|---|
| 아무 일도 없이 두 번 읽음 | 같다 |
| 다른 연결이 커밋 | 바뀐다 |
| 표지 연결이 읽기만 함 | 안 바뀐다 |
| 읽기 스냅숏이 열린 채 다른 연결이 커밋 | 바뀐다 |
| 표지 연결 자신이 커밋 | 안 바뀐다 |
| 체크포인트(truncate) | 바뀐다. 값이 더 자주 바뀌는 방향이라 안전하다 |

파일을 통째로 바꾸는 경우는 이 값이 보지 못한다. 설계는 `st_dev`와 `st_ino`의 변화를 보고 캐시를 끈다.

## 4. 구현 전후

두 쪽 모두 같은 합성 S3 사본(노드 120000)과 같은 장치에서 쟀다. 구현 전은 이 이슈의 기준 커밋 소스, 구현 후는 이 브랜치 소스다. 하네스 실행은 두 쪽 모두 소스 트리를 `PYTHONPATH`로 지정했다. (처음 두 실행은 가상환경이 주 체크아웃의 `opencrab`을 가져와 두 쪽 모두 같은 코드를 쟀다. 그 값은 버리고 다시 쟀다. 하네스 실행 때 가져오는 `opencrab`의 위치를 확인한다.)

판정: 이 합성 코퍼스에서 흔한 용어 전체 범위 p95가 요구치 안에 든다(구현 전에는 밖). 이 값은 웜 프로세스에서 쓰기가 없는 구간의 값이다. 동시 쓰기 구간의 p95는 줄지 않았다. 라이브 규모 사본의 쓰기 빈도에 따라 실제 이득이 정해지므로 라이브 이득은 배포 뒤 쓰기가 드문 구간의 실제 질의로 확인해야 한다.

## 5. 변이 검증 (2026-11-18)

게이트 레시피의 역변이 방식으로 제품 코드를 한 곳씩 바꾸고 해당 시험이 실패하는지 쟀다. 캐시 모듈과 캐시를 쓰는 호출 지점의 변이 26개, #569 경고 코드의 변이 14개를 돌렸다. 독립 검증자가 처음 지적한 두 변이(스냅숏을 고정하기 전에 두 번째 표지를 읽음, 표지 연결을 첫 읽기 때 엶)도 포함하며 시험을 더한 뒤 모두 실패로 바뀌었다. 처음 실행에서 캐시 쪽 네 개(읽기 쪽 세대 확인 제거, 통계 읽기의 세대 확인 제거, 표지 연결을 닫지 않음, 교체한 항목의 이전 바이트를 빼지 않음)와 #569 쪽 네 개(예산 경계 `>=`, 색인된 용어 수의 계산, 경고 문구의 예산 값, 앞선 경고의 유지)가 살아남았고 기준 변경 뒤 패턴이 맞지 않아 건너뛴 변이가 넷이었다. 살아남은 변이마다 시험을 더하거나 고친 뒤 다시 돌려 전량 실패로 바뀌었다. 재현은 변이마다 해당 함수를 바꾸고 `tests/test_node_bm25_cache.py`와 `tests/test_node_bm25_latency_warning.py`를 돌리는 것이다.

둘째 검증에서 표지 읽기의 실패 처리와 연결을 열 때의 파일 식별 비교가 시험에 잡히지 않는 것이 드러났다. 손으로 고른 변이만으로는 빈 곳이 남는다고 보고 캐시 모듈과 캐시를 쓰는 호출 줄 전체에 줄 단위 자동 변이(연산자 뒤집기, 비교 경계, 상수 뒤집기, 문장 삭제)를 돌렸다. 변이 166개 가운데 첫 실행에서 24개가 살아남았다. 반환값, 계수, 경계 값, 연결 닫기, 읽기 실패 처리를 직접 단언하는 시험을 더한 뒤 다시 돌렸더니 157개가 실패하고 9개가 남았다. 남은 9개 가운데 둘은 경고 기준 줄이며 지연 경고 시험이 실패시켰다. 나머지 일곱은 동작이 같은 변이(같은 표지에서 같은 순번이 나올 수 없는 비교, 같은 크기의 두 int64 배열 중 어느 쪽 크기를 빼도 같은 합, 연결이 이미 비었을 때의 꺼짐 표시 두 곳 네 변이)이거나 주석 단어가 바뀐 변이다.
