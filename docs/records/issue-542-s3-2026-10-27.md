# #542 S3 측정 기록 (2026-10-27)

이 기록은 2026-10-27에 관측한 값이다. 갱신하지 않는다. 판정 기준과 재현 명령은 `docs/issue-542-search-baseline.md`에 있다. 다음 측정은 새 날짜의 기록으로 남긴다.

## 1. 결론

- S3는 두 설정 모두 `verdict: COMPLETE`다. 누출, 중복, 범위 오류, 경고 누락, 동시 쓰기 누출과 중복은 0이다.
- 두 설정 모두 결합 `partial_silent`가 warm 반복 다섯 번 모두에서 나왔다(`common-heavy-1`). 설계 10절의 원문은 "누출이나 `partial_silent`가 나오면 그 단계는 끝까지 돌려 기록하되 다음 단계로 넘어가지 않는다."이다. 그래서 S4 확대 조건은 성립하지 않는다(8절).
- 같은 코드로 다시 잰 S1에서도 같은 질의가 `partial_silent`다. 이 결함은 규모와 무관하다. S2에서는 순위가 맞아떨어져 나오지 않았다(4절).
- 지연과 자원에서는 전체 범위 요청 p95, 동시 쓰기 중 전체 범위와 자동 선택 요청 p95, 동시 쓰기 지연 p95가 요구치를 넘었다(5절, 6절).

## 2. 조건

- 코드: 이 기록을 더한 브랜치의 부모 커밋(`origin/main`, #541, #550, #556, #567 포함). 하네스와 제품 코드는 바꾸지 않았다.
- 코퍼스: `scripts/search_corpus.py generate --preset S3 --seed 542`(생성 17.4초). 노드 120000, source 형태 30001, 질의 48(종류 16 x 3). 대형 팩 셋은 40000, 40000, 30000이다. 소형 팩 넷, 다른 소유자 팩 비공개 하나와 공개 하나, 미완성 팩, 무소속 문서, 측정 전용 팩이 들어 있다. 같은 시드로 한 번 더 생성한 코퍼스의 manifest는 바이트 단위로 같았다.
- 실행: 생성, 적재, 측정, 선행 점검, probe를 transient systemd 서비스(`CPUQuota=100%`, `Nice=19`, `IOSchedulingClass=best-effort`, `IOSchedulingPriority=7`, `LimitAS=2G`, `MALLOC_ARENA_MAX=2`, `PYTHONDONTWRITEBYTECODE=1`, `TMPDIR`은 디스크 경로)로 하나씩 돌렸다. 각 서비스는 python을 실행하기 직전에 같은 PID의 셸에서 다음을 파일로 남겼다.
  - 서비스 속성 `RuntimeMaxUSec`, `CPUQuotaPerSecUSec`, `LimitAS`, `Nice`, `IOScheduling*`
  - `/proc/<pid>/limits`의 주소 공간 상한, cgroup `cpu.max`, 환경의 `MALLOC_ARENA_MAX`, `TMPDIR`, `PYTHONDONTWRITEBYTECODE`, nice 값, ionice 값
- 위 기록은 첫 selftest를 뺀 열여덟 서비스 모두에 남았다. 모두 주소 공간 상한 2GiB, `cpu.max` `100000 100000`, nice 19, best-effort 7, `MALLOC_ARENA_MAX=2`였다. 첫 selftest는 기록 장치를 넣기 전에 돌렸으므로 같은 명령을 한 번 더 돌려 기록을 남겼다. 측정 보고서 `environment`에도 같은 주소 공간 상한과 `cpu.max`가 남았다. Python 3.13.5.

### 4.1 `partial_silent`: `common-heavy-1`

- 질의: 표지 토큰 하나와 흔한 단어 셋, 팩 미지정(전체 범위), `limit` 10이다. 정답은 둘이다. 하나는 대형 팩의 노드 형태 문서이고 하나는 공개 팩의 노드 형태 문서다. 둘 다 BM25 must-hit이고 FTS와 vector must-hit은 없다.
- 관측: BM25 레그는 두 정답을 1위와 2위로 냈다(분류 `pass`). 결합 결과는 BM25 1위만 담았다. BM25 2위인 공개 팩 정답은 창 밖이었다. 결합 경고는 없었다.
- probe: 같은 적재 디렉터리의 새 사본에서 하네스와 같은 요청을 `limit` 60으로 다시 불렀다. BM25 2위 정답의 결합 순위는 24였다. 이 정답은 FTS 목록과 vector 목록에 없었다.
- 원인: #556은 어휘 레그 1위만 반환 창 안에 둔다. #556 설계의 원문은 "2위 이하는 RRF 판단에 맡긴다."이다. 이 정답은 BM25 한 레그의 2위 값만 받는다. 흔한 단어 때문에 여러 레그에 나온 문서들이 RRF에서 앞선다. 그래서 정답이 창 밖으로 밀리고, 하네스 판정(설계 7.2절 5번)에서 `partial_silent`가 된다.
- 같은 코드의 S1: 같은 질의가 다섯 반복 모두 `partial_silent`였다. 놓친 정답은 대형 팩 쪽이었고 BM25 2위, 결합 순위 36이었다. S1에서는 결합 경고에 `fusion:` 경고가 하나 있었다(다른 레그의 1위가 창 밖). #556 설계 원문대로 "`fusion:` 경고만 붙이면 하네스 분류는 `partial_silent`로 남는다". 하네스는 `BM25 coverage`로 시작하는 경고만 coverage 경고로 센다.
- 같은 코드의 S2: 이 질의는 `pass`였다. #567 기록 8절의 S2 대조도 `common-heavy` 셋이 모두 결합 `pass`였다. `common-heavy`와 `common-only` 질의는 #567이 더했고, #567은 S2에서만 쟀다.
- 재현 조건: 이 기록의 코드, `--seed 542`, 프리셋 S1 또는 S3, 두 설정 어느 쪽이든 `run`. 보고서 `queries`에서 `qid`가 `common-heavy-1`인 항목의 결합 분류를 본다.
- 이 질의 밖에서 BM25 2위인 must-hit 정답은 S3에 아홉 개 더 있었다. 모두 결합 창 안이었다. 그 가운데 여섯은 FTS나 vector에도 나왔고, 셋은 BM25에만 나왔지만 흔한 단어가 없는 질의였다.

### 6.1 쓰기 지연 분해 (probe)

- 같은 적재 디렉터리의 새 사본에서 하네스의 쓰기 함수(`locked_write`)로 측정 전용 팩에 노드 300건을 초당 5건으로 썼다. 질의 없이는 p50 253.3ms, p95 257.5ms였다. 질의 스레드 하나가 질의 세트를 반복하는 동안에는 p50 575.0ms, p95 795.5ms였다.
- 같은 사본에서 쓰기 하나를 단계로 나누어 100번 쟀다(질의 없음, p50). 잠금 진입 0.2ms, `upsert_node_doc`(노드 BM25 색인 동기화 포함) 0.5ms, vector `upsert_texts` 255.5ms, `invalidate_bm25_cache` 0.1ms였다. 쓰기 시간의 거의 전부가 vector 쓰기다.
- vector 쓰기 p50은 같은 코드의 S1에서 39.3ms, S2에서 117.7ms였다. vector 행 수(20150, 61100, 120000)에 거의 비례한다. 행 하나에 약 2마이크로초다.
- `SqliteVecStore.upsert_texts`는 쓰기마다 vec0 가상 테이블에 소유자 조회(`node_id`를 배열 조건으로 묻는 `SELECT`)와 조건부 `DELETE`를 한다. 이 둘이 테이블을 훑는다는 추정은 질의 계획으로 확인하지 않았다.

## 8. 요구치 판정 요약과 S4 확대 조건

- 두 설정 모두 미충족은 여섯이다. `quality_combined_non_pass`(관측 2: `long-tail-1`, `common-heavy-1`), `quality_partial_silent`(관측 5), `latency_whole_scope_p95_ms`, `concurrent_whole_scope_p95_ms`, `concurrent_auto_p95_ms`, `write_p95_ms`다.
- 두 설정 모두 누출, 중복, 레그 non-pass, 범위 오류, 경고 누락, 자동 선택 오류, 명시 단일과 명시 다중과 자동 선택 요청 지연, 레그 지연, 동시 쓰기 중 명시 단일과 명시 다중 지연, cold, freshness, peak RSS, 색인 크기, WAL, 잠금 대기 요구치는 충족했다.

S4 확대 조건(설계 10절)은 다음과 같다.

- 앞 단계가 `COMPLETE`: 두 설정 모두 충족.
- 판정기 `selftest` 통과: 충족.
- peak RSS 추정: 필수 단계(적재, 두 실행) 가운데 최댓값 523.8MiB에 노드 비율(249000 / 120000)을 곱한 추정은 1087MiB로 1.6GiB 아래다.
- 누출과 `partial_silent`: 누출은 0이다. `partial_silent`는 두 설정 모두 5다. 이 조건이 성립하지 않는다.

그래서 S4로 넘어가지 않는다. 이 기록은 S4를 측정하지 않았다.
