# #580 잠긴 토큰 저장소의 인증 응답과 인증 대기의 시한 및 상한

## 결정

MCP HTTP 인증(`opencrab/mcp/http_app.py`)에서 토큰 조회가 저장소 오류로 끝나면 `_verify`가 예외를 삼키고 `None`을 돌려주고, 호출자는 그 `None`을 무효 토큰과 같은 401로 바꾼다. 저장소가 잠겨 조회를 끝내지 못한 요청과 무효 토큰의 요청이 구분되지 않는다. 인증 조회를 도는 풀(`mcp-auth`, #577)의 대기열에는 상한이 없고 요청별 시한도 없다.

1. 저장소를 일시적으로 쓰지 못해 조회를 끝내지 못하면 503 + `Retry-After`로 응답한다. 401은 저장소가 조회를 끝내 토큰이 무효로 확인된 경우, 조회할 대상이 없는 경우, 일시 장애로 분류하지 않는 오류에 남긴다. 마지막은 종전 동작을 그대로 둔 것이며 토큰이 무효라는 확정 증거가 아니다. 해당하는 오류는 오류 분류 절이 열거한다.
2. 요청이 인증 결과를 기다리는 시간에 시한을 둔다(`_AUTH_DEADLINE_SECONDS`). 시한을 넘으면 같은 503이다.
3. 인증 대기열에 크기 상한을 둔다(`_AUTH_QUEUE_LIMIT`). 가득 차면 풀에 넣지 않고 즉시 같은 503이다.
4. 인증 풀을 `ThreadPoolExecutor`에서 크기가 정해진 `queue.Queue`와 전용 스레드 하나(`_AuthWorker`)로 바꾼다. `ThreadPoolExecutor.submit`은 항목 삽입과 스레드 시작을 한 호출에서 하고 그 사이에 실패할 수 있어, 호출자가 삽입 여부를 알 수 없다. 별도 건수 카운터는 이 모호함 때문에 실패 경로마다 소유 규칙을 요구한다. `put_nowait`는 삽입하거나 `queue.Full`을 내며 둘 중 하나로만 끝난다.
5. 자격 증명 추출(`_presented`)을 저장소 조회(`_lookup`)에서 분리한다. 추출은 이벤트 루프에서 돌고, 조회가 필요 없는 요청은 풀에 넣지 않는다.
6. 운영은 인증 워커에 종료를 걸지 않는다. 워커는 프로세스 단위 데몬 스레드이고 프로세스가 끝날 때 대기 항목과 함께 사라진다. 서버 종료 중에 인증 요청이 끝까지 처리되는 것은 이 이슈의 받아들임 기준 밖이다. 앞선 설계안은 앱 종료 때 대기 항목에 응답하는 종료 의미론(닫힘 표시, 대기 항목 거부)을 요구했으나 운영에 그런 종료 경로가 없어 철회했다(`_startup_registry_check` lifespan은 `yield`만 하고 종료 처리가 없고, `_POOLS`는 모듈 수준이다). 워커에는 시험 fixture가 스레드를 정리하려고 쓰는 `stop_for_tests()` 하나만 둔다.

하지 않는 일: SQLite 저널 모드와 busy timeout 변경, 운영자 설정 추가, 인증 결과 캐시, 회로 차단기, PostgreSQL 문장 시한 설정, REST API(`apps/api/main.py`의 `require_auth`) 변경, 쓰기와 읽기 도구 풀 변경, 인증 워커의 종료 의미론. REST의 잠금 오류가 500으로 끝나는 문제와 `SQLStore`의 연결 실패 로그가 예외 원문을 싣는 문제는 후속 이슈로 올린다.

401 대신 503을 고르는 근거: 인증 규격은 무효 토큰에 401을 요구하고 클라이언트는 `WWW-Authenticate`를 보고 OAuth 흐름을 시작한다. 503은 인증 도전이 아니고 `Retry-After`는 RFC 9110이 503과 함께 쓰는 헤더다. MCP TypeScript SDK의 Streamable HTTP 클라이언트는 5xx 전용 분기가 없어 일반 오류로 던지고 재인증하지 않는다. Claude Code 내부 동작은 확인하지 못했다. 이 변경은 클라이언트의 자동 재시도를 주장하지 않는다.

## 응답 계약

| 상황 | 응답 |
|---|---|
| 저장소 정상, 유효 토큰 | 200 (변경 없음) |
| 저장소 정상, 무효 토큰, 폐기된 토큰, 비활성 사용자의 토큰 | 401 + `WWW-Authenticate: Bearer` (변경 없음) |
| 자격 증명 없음, 비 Bearer 헤더, 빈 헤더, 공백뿐인 토큰 | 401 (변경 없음). 대기열이 가득 차 있어도 같다 |
| 저장소 파일 없음, 테이블 부재, 열 부재 | 401 (변경 없음) |
| 일시 저장소 오류(아래 분류), 연결 실패, 시한 초과, 대기열 가득 참 | 503 + `Retry-After: 5` + `Cache-Control: no-store`, `WWW-Authenticate` 없음, 고정 본문 |

후보 토큰이 있는 요청은 아래 오류 분류가 503으로 정한 저장소 장애 동안 토큰이 유효한지 판정할 수 없으므로 무효 토큰이어도 503이다. 분류하지 않은 저장소 오류는 종전처럼 401이다. 받아들임 기준의 "기존 무효 토큰 401 경로"는 저장소가 정상일 때의 경로다. `Retry-After`는 재시도 권고 간격이며 잠금 해제 시각의 예측이 아니다.

## 오류 분류(`_lookup`)

503으로 올리는 경우:

- SQLite 잠금: `sqlalchemy.exc.OperationalError`이고 `orig`가 `sqlite3.OperationalError`이며 `orig.sqlite_errorcode & 0xFF`가 5(`SQLITE_BUSY`) 또는 6(`SQLITE_LOCKED`)이다. 프로젝트가 요구하는 Python 3.11 이상에서 이 속성이 있다.
- 서버형 연결 계열 오류: `OperationalError`이고 `orig`가 `sqlite3.Error`가 아닌 경우 가운데, `connection_invalidated`가 참이거나 `orig.pgcode`가 없거나 SQLSTATE가 `08xxx`, `57P01`, `57P02`, `57P03`, `53300`이다. 접속 단계(핸드셰이크) 오류는 `pgcode`를 싣지 않는다고 가정한다. 그래서 접속 단계의 비밀번호 인증 실패도 503이다. 이 경우를 코드로 가를 수 없고, 접속 실패는 토큰의 유효성과 무관한 서버 설정이나 장애이므로 유효 토큰을 401로 거부하지 않는 쪽이 이슈의 의도에 맞다.
- 연결 풀 대기 초과(`sqlalchemy.exc.TimeoutError`).
- `_auth_store`가 `available == False` 저장소를 돌려준 경우.

그 밖의 예외는 이전처럼 `None`(401)이다. 해당하는 예: SQLite의 비잠금 `OperationalError`(테이블 부재, 열 부재, 파일 열기 실패, 입출력 오류), 연결 이후 질의 단계의 PostgreSQL 오류(`28P01`, 디스크 가득 참, 질의 취소, 교착), 서버형 `ProgrammingError`. 로컬 모드에서 DB 파일이 없으면 `_auth_store`가 `None`을 돌려주므로 이전처럼 401이다.

## 구조

### 추출과 조회의 분리

- `_presented(request, creds)`: 현재 `_check`의 분기 규칙을 그대로 옮긴다. 헤더가 있으면 헤더가 요청을 결정하고(Bearer 형식이면 그 토큰, 아니면 없음), 헤더가 없고 `allow_query_token`이면 쿼리 `token`을 쓴다. 후보가 없으면 `None`이다. 입출력이 없어 이벤트 루프에서 돈다.
- `_check_off_loop`: 후보가 `None`이거나 공백뿐이면 풀에 넣지 않고 401이다. 후보가 있으면 `_lookup(presented)`를 워커에 제출한다. 결과 `None`은 401, `Principal`은 반환이다.
- `_lookup`: 종전 `_verify`를 대신한다. 분류에 따라 `None`을 돌려주거나 503 `HTTPException`을 올린다.
- 바뀌는 부작용 하나: 공백뿐인 쿼리 토큰은 이전에 401을 내기 전에 인증 저장소를 열고 `auth_sql`에 캐시했다. 이제 열지 않는다. 응답은 같다.

### 인증 워커(`_AuthWorker`)

- 구성: 크기 `_AUTH_QUEUE_LIMIT`의 `queue.Queue`, 스레드 하나(이름 `mcp-auth`, 데몬), 락 하나(`_lock`). 프로세스 단위이고 `_POOLS`와 같은 자리에서 같은 락으로 처음 쓸 때 만든다. 실행 중인 조회 하나는 대기열 밖이다.
- `submit(job)`: `_lock` 안에서 (1) 스레드가 없거나 죽었으면 새 `Thread`를 시작(실패하면 대기열에 아무것도 넣기 전에 예외가 나간다. 다음 제출이 다시 시도한다), (2) `put_nowait(job)`: 가득 차면 `False`, 넣었으면 `True`를 돌려준다.
- 스레드 본문: 항목을 꺼내 `job.run()`을 부르는 루프다. `job.run()`은 조회 함수의 `BaseException`까지 잡아 요청의 future에 전달하므로 조회 함수의 예외로는 스레드가 죽지 않는다. 죽는 경우는 루프 자체의 실패뿐이다. 죽은 뒤에도 대기열은 남고 다음 `submit`이 새 스레드를 시작해 이어서 처리한다.
- `_AuthJob`: 조회 함수, 이벤트 루프, 요청이 만든 asyncio future, 포기 표시를 가진다. `run()`은 포기 표시가 있으면 조회하지 않고 끝낸다. 없으면 조회하고 결과나 예외를 `loop.call_soon_threadsafe`로 전달한다. 전달 함수는 future가 이미 끝났으면(취소 포함) 아무것도 하지 않고, 루프가 닫혀 `RuntimeError`가 나면 삼킨다.
- 대기 쪽: `_check_off_loop`가 future를 만들어 제출하고 `asyncio.wait({future}, timeout=_AUTH_DEADLINE_SECONDS)`로 기다린다. `submit`이 `False`면 곧바로 503이다. 시한이 지나면 포기 표시를 걸고 `future.cancel()`을 부른 뒤 503을 올린다. task 취소 등 그 밖의 예외로 기다리기를 그만두면 `BaseException`을 잡아 같은 포기 표시와 `future.cancel()` 뒤 다시 올린다. 포기한 항목은 대기열에 남고 워커가 꺼내는 즉시 건너뛴다.
- 상한: 대기열의 물리 항목 수가 `_AUTH_QUEUE_LIMIT`를 넘지 못한다. 포기한 항목도 대기열에 있는 동안은 이 상한에 든다. 보관 시간에는 상한이 없다.
- 시한: `_AUTH_DEADLINE_SECONDS = 8.0`은 SQLite busy timeout(5.0초)보다 길다. 대기 없이 실행된 조회가 잠금에 걸리면 busy timeout에서 스스로 오류로 끝나고 분류된다. 앞선 조회 뒤에서 기다린 요청은 시한이 먼저 끝날 수 있다. 두 경우 응답은 같은 503이다. 실행 중인 조회는 중단할 수 없다. SQLite 잠금 대기는 busy timeout이 묶고 다른 단계는 묶지 않는다.
- 잠금과 스레드 상태: `_lock`은 `submit`만 쥔다. 그 안에서 스레드 확인과 시작과 `put_nowait`가 일어난다. 워커 스레드는 `_lock`을 쥐지 않고 큐 내부 잠금만 쓴다. `job.run()`의 `call_soon_threadsafe`는 `_lock` 밖에서 일어난다. 그래서 잠금 순환이 없다. 제출 둘이 겹쳐도 `_lock`이 스레드 시작을 직렬화하므로 스레드는 하나다.
- 시험 전용 정지 `stop_for_tests()`: 이름과 docstring이 시험 전용임을 밝힌다. 종료 표지 항목을 `put(timeout=…)`으로 넣고 스레드를 `join`한다. 대기열에 남은 요청의 응답은 약속하지 않는다. 호출자(시험 fixture)가 대기열을 비운 뒤 부른다. 운영 코드(`opencrab/`, `apps/`)에서 이 함수를 호출하지 않는다. 시험이 grep으로 확인한다.
- 데몬 스레드의 효과: 앞선 `ThreadPoolExecutor` 스레드는 비데몬이었고 인터프리터 종료 때 `concurrent.futures`의 종료 처리가 풀 스레드를 `join`했다. 그래서 실행 중이던 조회와 대기 항목이 끝날 때까지 프로세스 종료가 기다렸다. 새 워커는 데몬이라 종료를 기다리지 않는다. 관측 가능한 차이는 둘이다. (1) 종료 중에 도착했거나 종료 전에 받았지만 아직 끝나지 않은 인증 요청(시한이 지나 응답을 받은 뒤 남은 조회 포함)은 끝까지 처리되지 않고 사라진다. (2) 프로세스 종료가 인증 조회의 완료를 기다리지 않는다. 잠금에 걸린 조회가 있으면 앞선 구현은 busy timeout(5.0초)까지 종료가 늦어질 수 있었다.
- 데몬 스레드가 사라져도 안전한 근거: 애플리케이션은 인증 경로에서 쓰지 않는다. `_auth_store`는 `SQLStore(create_tables=False)`로 열어 DDL을 실행하지 않고, `_connect`는 `PRAGMA foreign_keys=ON`과 `SELECT 1`만 하며, `verify_token`은 `SELECT`만 하고 `last_used_at`을 갱신하지 않는다. 다만 이것이 SQLite 파일의 물리적 불변을 뜻하지는 않는다. SQLite는 읽기 전에 hot journal이 있으면 복구하며 페이지를 쓰고 저널을 지운다. 복구 도중 프로세스가 다시 끝나도 일관성을 지키도록 SQLite가 기록과 저널 제거의 순서를 정한다. 그래서 안전의 근거는 파일 불변이 아니라 애플리케이션의 쓰기 부재와 SQLite의 복구 절차다. 복구 도중 프로세스를 끊는 실험은 하지 않았다.

#577이 보장한 성질과의 대응: 조회는 이벤트 루프 밖 단일 스레드(`mcp-auth`)에서 돈다. 인증 동시성은 1이다. 프로세스 단위 지연 생성은 `_POOLS` 자리로 유지된다. 시작 전에 포기한 대기 작업은 실행되지 않는다(포기 표시). 인증 풀 이름 `"auth"`는 `_pool()`이 더 이상 만들지 않는다. 앞선 구현과 달라진 것은 위 데몬 스레드의 효과 둘이다.

### 로그

503마다 WARNING 한 줄을 남긴다. 내용은 고정 사유 코드(`store-busy`, `store-unavailable`, `deadline`, `queue-full`)뿐이다. 같은 사유는 10초에 한 번만 남긴다. 예외 원문, SQL, 토큰 해시를 싣지 않는다. `docs/observability-rules.md` 판정: 새 사용자 작업 경계나 trace를 만들지 않고 기존 `logger`에 고정 코드만 기록한다. 이 로그는 상시 수집과 집계가 아니다.

### SOLID 판정

- 단일 책임: 추출(`_presented`), 조회와 분류(`_lookup`), 제출과 시한(`_check_off_loop`), 대기열과 스레드(`_AuthWorker`), 작업 수명(`_AuthJob`)으로 나눈다. 현재 `_check` 하나가 루프에서 즉시 필요한 추출과 풀에서 도는 조회를 겸하고 두 호출자 집단이 갈리므로 이 경계로 나눈다.
- 개방 폐쇄: 복사해 값만 바꾸는 분기가 없다. 해당 없음.
- 리스코프: 새 예외는 기존 `HTTPException`이고 호출자는 401과 503을 같은 방식으로 전파한다. 시험 대역 `verify_token`은 기존 시그니처를 지킨다.
- 인터페이스 분리: `_lookup`은 토큰 문자열만 받는다. 요청 객체를 워커로 넘기지 않는다.
- 의존 역전: 시험이 시한과 대기열 크기를 모듈 상수로, 워커를 `_POOLS` 자리에서 바꿔 끼운다. 구현이 하나뿐이므로 인터페이스 타입을 만들지 않는다.

## 기존 시험의 변경

- `tests/test_auth_boundary.py::TestAuthStoreDoesNotCacheFailure`: 연결 실패 한 번 동안 유효 토큰이 받는 응답을 401에서 503으로 바꾼다. 이 시험의 목적(실패한 저장소를 캐시하지 않고 다음 요청에서 회복)은 그대로다.
- `tests/test_http_app_offload.py`: (1) `env.widths()`가 `mcp-auth: 1`을 포함한다는 단언 둘을 행동 단언으로 바꾼다. 조회 대역이 `threading.current_thread()` 객체를 기록하고, 동시 요청 여럿에서 객체 집합 크기가 1이며 이름이 `mcp-auth` 접두임을 단언한다. 첫 조회가 막힌 동안 둘째 조회가 시작하지 않음을 단언하고(짧은 상한의 부재 확인), 풀면 둘째가 이어서 실행됨을 단언한다. 살아 있는 `mcp-auth` 스레드 수가 정확히 1임을 `threading.enumerate()`로 단언한다. 쓰기와 읽기 풀의 폭 단언은 그대로다. 단언을 지우거나 약하게 하지 않는다. (2) fixture `env`, `cold_real`이 `_POOLS`를 교체할 때 인증 워커를 `stop_for_tests()`로 정리한다. 이 변경은 PR 본문에 드러낸다.

## 시험과 역변이 대응표

새 파일 `tests/test_mcp_auth_unavailable.py`. 모든 대기는 상한이 있고 그 상한은 하네스 종료 조건이며 합격 조건이 아니다. 막는 대역은 작업 시작을 알리는 이벤트를 먼저 세우고 풀려날 때까지 기다린다. 변이는 원래 작업 트리가 아니라 폐기할 격리 checkout에서 한다.

| # | 시험 | 수정 전 | 검출하는 변이 |
|---|---|---|---|
| 1 | 실제 잠금(별도 `sqlite3` 연결의 `BEGIN EXCLUSIVE`, busy timeout 설정값 그대로): 유효 토큰이 503 + `Retry-After`, `WWW-Authenticate` 없음. 잠금을 풀면 같은 앱이 200. 쿼리 토큰 경로는 busy timeout을 줄인 같은 시험 | 401로 실패(RED) | 잠금 분류를 되돌림 |
| 2 | POST, GET, DELETE가 같은 503(`verify_token`에 SQLite 잠금 예외 주입) | 401로 실패 | 잠금 분류를 되돌림 |
| 3 | 분류: 비잠금 `OperationalError`, 일반 예외, 빈 DB 파일, `28P01`은 401. `pgcode` 없음, `08006`, `57P01`, `53300`, `connection_invalidated`, 풀 `TimeoutError`, `available == False`는 503. 무효 토큰은 `WWW-Authenticate` 있는 401 | 일부 실패 | 서버형 분류를 `OperationalError` 전체로 넓힘 |
| 4 | 대기열이 가득 찬 동안 자격 증명 없음, 비 Bearer, 빈 헤더, 공백 헤더 토큰, 공백 쿼리 토큰은 풀에 넣지 않고 401(제출 항목 수 불변) | 대기열 계측(`queued`)이 없어 전제 단계에서 실패한다. 이 입력들의 응답은 base도 401이다 | 공백 토큰 사전 거부를 지움 |
| 5 | 상한: 대기열 크기를 줄이고 조회를 막아 쌓는다. 막힌 조회 하나와 대기열 크기만큼은 받고 다음 요청은 즉시 503. 풀리면 받은 요청이 모두 200 | 대기열 계측 전제에서 실패한다(행동으로는 상한 초과 요청이 대기한다) | 대기열 크기를 무제한으로 바꿈 |
| 6 | 시한: 막힌 조회 뒤의 요청이 시한에 503. 포기한 작업은 풀린 뒤 조회를 실행하지 않는다(대역 호출 횟수). 끝나면 대기열이 빈다 | 대기열 계측 전제에서 실패한다 | 시한 제거, 포기 표시 무시 |
| 7 | 반복 포기: 대기열 크기 3, 시한 짧게. 막힌 조회 하나 뒤에서 여러 번 보낸다. 물리 대기열 크기가 3을 넘지 않고 가득 찬 뒤는 즉시 503 | 실패 | 대기열 크기를 무제한으로 바꿈 |
| 8 | 스레드 시작 실패: 시작이 예외를 던지게 한다. 요청은 항목을 남기지 않고 예외로 끝난다. 원인을 없애면 다음 요청이 시작하고 200. 상한보다 많이 반복해도 회복 | base에서 `DID NOT RAISE`로 실패한다(신규 구조의 시작 경로가 없다) | 시작 실패 뒤 참조를 남겨 재시작하지 않음 |
| 8a | task 취소: 대기 중 요청 task를 취소하면 그 작업이 조회를 실행하지 않고 대기열이 빈다 | base에서 대기열 계측 전제로 실패한다 | 대기 이탈 처리를 `BaseException`에서 `Exception`으로 바꿈 |
| 8b | 늦은 결과: 시한으로 포기한 뒤 작업이 끝나도(정상 결과, 조회 밖으로 나온 503, 조회가 잡지 않는 `BaseException`) 루프 예외 처리기에 `InvalidStateError`와 "never retrieved"가 접수되지 않는다. 요청이 응답하고 조회를 풀기 전에 그 future가 취소돼 있음을 보고, 작업의 `run`이 끝났음을 확인한 뒤 작업과 future 참조를 놓고 `gc.collect()` 뒤 접수 목록이 빔. 루프가 닫힌 뒤 끝나도 스레드가 죽지 않고 다음 작업을 처리 | base에서 `_AuthJob` 부재(`AttributeError`)로 실패한다 | 전달 함수의 `future.done()` 검사를 지움 |
| 8c | 스레드 사망 뒤 회복: `_AuthJob.run`을 예외로 바꿔 루프를 죽인다. 대기열에 항목이 남은 상태에서 다음 요청이 새 스레드를 시작하고 남은 항목과 새 요청이 모두 응답을 받는다. 조회 함수의 `BaseException`은 그 요청만 오류이고 스레드는 산다 | base에서 `_AuthJob` 부재(`AttributeError`)로 실패한다 | 죽은 스레드 재시작 검사를 지움 |
| 9 | 같은 사유의 503 반복이 WARNING 한 줄이고 로그에 토큰과 SQL이 없다 | base에서 503 대신 401을 받아 실패한다 | 로그 제한 삭제 |
| 10 | #577 대체 단언(위 기존 시험의 변경 (1)): 스레드 객체 집합 크기 1, 첫 조회가 막힌 동안 둘째 조회 미시작, 살아 있는 `mcp-auth` 스레드 수 정확히 1 | base에서 구조 단언이 실패한다(base의 스레드 이름은 `mcp-auth_0`이고 풀 폭 단언은 executor를 가리킨다) | 워커를 둘로 늘림(둘이 같은 락으로 소비를 직렬화하는 변이 포함) |
| 11 | `stop_for_tests()`가 스레드를 끝내고, `opencrab/`와 `apps/` 소스에 이 이름의 호출이 없다(정의 줄 제외) | base에서 `_AuthWorker` 부재로 실패한다 | 운영 코드에 호출을 넣음 |

"수정 전" 칸은 base(`origin/main`)에 이 변경의 시험 파일을 얹어 돌린 관측이다. 대기열 계측(`queued`)과 `_AuthWorker`가 base에 없어서 일부 시험은 행동 단언에 닿기 전에 전제 단계에서 실패한다. 받아들임 기준의 실제 잠금 시험은 base에서 401로 실패한다.

회귀: `tests/` 전량을 base와 작업에서 같은 조건으로 돌려 대사한다. 기존 인증 시험이 위 두 시험 변경을 뺀 나머지에서 상태가 같아야 한다.

## 받아들임 기준

- 토큰 저장 파일이 잠긴 동안의 유효 토큰 요청은 401이 아니라 503 + `Retry-After`다. 잠금이 풀리면 같은 요청이 200이다.
- 인증 대기에는 요청별 시한이 있고 대기열에는 크기 상한이 있으며, 둘 다 시험이 고정한다.
- 응답 계약 표의 "변경 없음" 행은 바뀌지 않는다.
- 린트가 깨끗하고 전량 회귀 대사에서 base 대비 의도되지 않은 상태 변화가 없다.

## 가정

- 운영 `opencrab.db`는 롤백 저널 모드다. 틀려서 WAL이면 잠금 창이 좁아질 뿐이고 분류는 오류가 났을 때만 작동하므로 정확성에는 영향이 없다.
- Claude Code가 5xx에서 OAuth를 시작하지 않는다. SDK 구현으로 확인했고 Claude Code 자체는 확인하지 못했다. 틀리면 이 변경의 효과는 재시도 가능성을 표준 방식으로 알리는 데 그친다.
- 접속 단계의 PostgreSQL 오류는 `pgcode`를 싣지 않는다.
- 클라이언트 연결 끊김이 요청 task 취소로 이어지는지는 서버 구성에 따른다. 이어지지 않아도 요청이 시한에서 끝나므로 안전하다.
