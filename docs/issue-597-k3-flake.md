# 이슈 597: K3 소진 중 강제 종료 주입이 부모 지연에 기대는 잔여 경쟁

설계 정본은 `docs/issue-542-fault-injection.md`다. 같은 형태를 C3와 K1에서 고친 내용은 `docs/issue-596-c3-flake.md`에 있다. 이 문서는 K3에 남은 같은 형태의 원인과 수정 설계를 적는다.

## 1. 원인

K3 시나리오는 자식 `search`가 pending 키를 소진하는 동안 하네스가 `ro_pending`을 `POLL` 간격으로 읽다가, 남은 pending 수가 처음보다 작고 0보다 크면 `SIGKILL`을 보낸다. 판정이 부모의 읽기 속도에 걸려 있다.

- 자식은 검색을 반복한다. 검색마다 `_node_bm25_try_drain`이 시간 예산 안에서 소진 트랜잭션을 하나 이상 연다. 트랜잭션 하나는 묶음 하나(`--slow-drain`이 정한 크기)를 처리하고 커밋한다. 검색 사이에 자식은 잠시 쉰다. 모든 pending을 소진하면 종료 코드 0으로 끝난다.
- 부모가 "줄기 시작했다"는 읽기 뒤에 신호를 보내기까지 지연되거나, 첫 읽기 자체가 지연되면 자식이 소진을 끝내고 종료한다. 그러면 `alive`가 거짓이고 `rc`가 0이며 `p1`이 0이어서 `not_injected`다.
- 이 장치에서 전체 소진은 초 단위로 끝나므로 여유가 작다. 실제 CI 실패는 관측하지 않았다. 잠재 위험이다.

이 장치의 재현은 3절의 부모 지연 시험이다. 수정 전에 `alive=False`, `rc=0`, `p1=0`으로 `not_injected`를 낸다.

제품 코드의 결함은 찾지 못했다. 소스상 `_node_bm25_try_drain`은 `BEGIN IMMEDIATE` 아래에서 `drain`을 부르고 `commit`한다. 강제 종료는 미커밋 묶음을 버리고 앞서 커밋한 묶음을 남긴다. 이것이 K3가 검사하려는 성질이다.

K3 외에 폴링 뒤 신호를 보내는 호출은 남지 않는다. `child.signal`의 호출자는 C3와 K1(`held` 줄 뒤), K2(`inside` 줄 뒤), K3 넷이며 K3만 폴링이었다.

## 2. 수정

판정을 시간이 아니라 자식의 사건에 건다. #596의 `--hold-at-docs`와 같은 기법을 소진 단계에 옮긴다.

- 자식 `search`에 `--hold-at-drain <N>`을 더한다. 자식은 `_node_bm25_sqlite.drain`을 감싼다. 키를 하나 이상 처리한 `drain` 호출만 센다. 처리량이 0인 호출(pending이 묶음 크기의 배수일 때 소진 루프가 한 번 더 부른다)은 세지 않고 멈추지도 않는다. N번째로 센 호출이 키를 소진한 직후, 호출자가 아직 커밋하지 않은 상태에서 `held` 줄을 내고 신호를 기다린다. 줄에는 센 호출 번호와 그 호출이 처리한 키 수를 싣는다. 자식 자신의 `alarm`(자식 제한 시간)은 그대로 남아 대기를 끝낸다.
- K3는 N을 2로 둔다. 첫 소진 트랜잭션은 커밋되어 pending이 줄어든 채 남는다. 둘째 소진 트랜잭션은 키를 처리한 뒤 커밋하지 않은 채 멈춘다. 그래서 신호는 항상 앞선 커밋이 하나 이상 있고 미커밋 쓰기가 있는 트랜잭션 안에 떨어진다. 종료 뒤 pending 수는 처음보다 작고 0보다 크다.
- 하네스는 `held` 줄을 기다린 뒤 신호를 보낸다. 자식이 멈춰 있으므로 부모가 자식 제한 시간 안에서 얼마나 멈추든 자식은 살아 있고 소진은 그 지점에서 더 나가지 않는다. 부모가 제한 시간을 넘겨 멈추면 `alarm`이 자식을 끝내고 하네스는 `not_injected`를 낸다. 이 보장은 그 범위로 한정하며 `alarm`은 제거하지 않는다.
- 주입 확인은 `held` 줄이 왔고, 그 줄이 처리한 키 수가 0보다 크며, 신호 직전 자식이 살아 있었고, 회수한 종료 상태가 `-SIGKILL`이며, 종료 뒤 pending 수가 처음보다 작고 0보다 큰 것이다.

원래 패턴의 전제 점검(#596의 `Scenario.hold_backfill`은 backfill 단계에 맞춰져 있다):

- 멈춘 시점에 커밋하지 않은 쓰기가 있다: `_node_bm25_try_drain`이 `BEGIN IMMEDIATE`를 연 뒤 `drain`을 부르고 그 반환 뒤에 `commit`한다. 감싼 함수는 원래 `drain`이 키를 재색인하고 pending 행을 지운 뒤에 멈추므로 쓰기가 트랜잭션 안에 남는다. 줄에 처리한 키 수를 실어 부모가 이를 확인한다.
- 자식이 살아 있다: 멈춘 자식은 `time.sleep`에 있고 `alarm`만 끝낼 수 있다.
- 부모의 읽기가 막히지 않는다: 부모의 `ro_pending`은 읽기 전용 연결이다. 쓰기 잠금을 쥔 자식이 멈춰 있어도 WAL 읽기는 커밋된 상태를 본다. K1의 기존 멈춤이 같은 조건이다.
- 앞선 커밋이 있다: N을 2로 두고 키를 처리한 호출만 세므로 pending이 한 묶음 이상 줄어든 상태가 보장된다. 첫 `drain`이 모든 키를 처리해 키를 처리하는 둘째 호출이 없으면 자식은 멈추지 않고 끝나 `held` 줄이 없다. 그 경우 하네스는 `not_injected`를 낸다. 대형 팩의 키 수가 묶음 크기보다 커야 하는 조건은 기존 판정(`0 < p1 < p0`)과 같다.
- 시간 예산을 쓰는 곳이 없다: `--slow-drain`이 정한 소진 시간 예산은 한 검색 안에서 묶음을 몇 개 소진하는지만 정한다. 멈춤 지점은 `drain` 호출 횟수로 정하므로 그 값에 기대지 않는다.

공통 부분을 새로 추상화하지 않는다. 호출자는 K3 하나이고 대기 한 줄(`wait_tag`)이면 된다. `Scenario.hold_backfill`은 backfill 전용이며 건드리지 않는다.

SOLID 판정: 새 단위는 actor 옵션 하나와 `search` actor 안의 감싸기 하나다. 분기를 늘리는 데이터화나 추상화는 없다. 호출자가 하나여서 단일 책임과 인터페이스 분리 판정에 걸리는 경계도 없다. 제품 코드는 바꾸지 않는다.

## 3. 시험

- `tests/search_faults_timing_child_596.py`는 부모 쪽 `ro_status`에 더해 `ro_pending`이 읽은 뒤에도 지정한 시간만큼 멈추게 한다. K3는 `ro_pending`으로 진행을 읽는다.
- `tests/test_search_faults.py::test_signal_injection_does_not_depend_on_runner_speed`에 K3 경우(`parent_stall_drain`)를 더한다. 부모가 소진 전체보다 오래 멈춰도 `COMPLETE`를 요구한다. 수정 전 코드에서는 `not injected: ['K3']`로 실패하고 수정 뒤에는 통과한다.
- 역변이 둘: (a) K3를 수정 전 형태(`--hold-at-drain`을 넘기지 않는 폴링 후 신호)로 되돌린다. (b) 자식의 `--hold-at-drain` 멈춤을 제거한다. 둘 다 위 경우가 실패해야 한다. (b)는 `not_injected`다. 멈춤 장치를 설치하지 않으면 `held` 줄이 오지 않고, `held` 줄을 낸 뒤 멈춤(`time.sleep`)만 빼면 자식이 살아 있지 않아 신호 직전 확인이 실패한다. 자식이 멈춘 채로 부모만 폴링으로 되돌리는 변이는 자식이 멈춰 있어 판정이 부모 지연에 기대지 않으므로 같은 동작이고 실패하지 않는다.
- 이 경우의 RED는 부모 지연이 수정 전 소진 전체보다 길다는 전제에 선다. 이 장치에서 수정 전 코드의 소진은 5초보다 짧게 끝난다. 더 느린 러너에서 수정 전 코드는 RED가 흐려질 수 있으나 수정 뒤 코드의 GREEN은 지연 길이에 기대지 않는다.

재현 명령(기준선 코퍼스는 `docs/gate-recipes.md`의 S0 절차로 만든다):

```bash
python tests/search_faults_timing_child_596.py 5 1 run --corpus <코퍼스> --work <적재> --run-root <루트> --out <보고서> --scenarios K3   # 부모 지연
```

## 4. 범위 밖

- 제품 코드는 바꾸지 않는다.
- R1의 `--step-delay`가 만드는 겹침 구간은 자식의 시간 대기에 기대는 설계이며 이 이슈가 다루지 않는다(`docs/issue-596-c3-flake.md` 2절).
- 시험 시간과 다른 시나리오의 시간 의존 점검은 다루지 않는다.
