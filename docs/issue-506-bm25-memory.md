# #506 serve 상주 메모리 증가 설계

## 범위와 판정

`opencrab serve --transport http` 프로세스의 RSS가 재기동 뒤 쓰기 부하 아래서 계속 늘어난다. 원인은 BM25 인덱스 캐시(`opencrab/ontology/query.py`의 `_Bm25CacheWorker`, `opencrab/ontology/bm25.py`의 `BM25Index`)다. 이 변경은 다섯 가지를 고친다. 워커가 지난 인덱스를 붙들고 있는 참조, 토큰 표현, 인덱스 입력의 크기, 쓰기 폭주 중의 연속 재빌드, 재빌드 뒤 반환되지 않는 메모리다. 로컬 GGUF 임베딩 폴백, 벡터 ANN 캐시, 저장소 스키마는 건드리지 않는다.

## 근본원인

`HybridQuery`의 BM25 캐시는 doc 스토어의 최신 `_BM25_NODE_LIMIT`개 노드(기본 5만)를 한 인덱스로 보관한다. 다음 다섯 성질이 겹친다.

1. **워커가 지난 인덱스를 붙들고 있다.** `_rebuild_loop`의 지역 변수 `state`, `candidate`, `observation`은 한 회차가 끝나도 다음 회차가 같은 이름에 새 값을 넣을 때까지 산다. 새 상태를 게시한 뒤에도 `state`가 직전 인덱스를 가리킨다. 빌드 중 쓰기로 폐기된 `candidate`는 다음 빌드 동안 산다. 그래서 유휴 시에도 인덱스가 둘 이상 살고, 폐기가 이어지면 셋 이상 산다. 합성 데이터 벤치에서 이 지역 변수만 비우자 재빌드 뒤 정상 RSS가 약 3분의 1 줄었다.
2. **토큰이 문자열 객체의 리스트다.** `BM25Index.build`는 문서마다 `tokenize()` 결과를 그대로 보관한다. 같은 토큰이 문서마다 새 `str` 객체다. 한글 2-gram과 3-gram이 토큰 수를 두 배 이상으로 늘린다. 같은 벤치에서 토큰 리스트가 인덱스 메모리의 대부분이었다.
3. **상한이 건수뿐이다.** 창은 `ORDER BY updated_at DESC`로 고른다. 새 쓰기가 대화 로그의 긴 TextUnit이면 창에서 짧은 노드를 밀어내 창의 바이트 합이 늘어난다. 라이브 doc 스토어의 읽기 전용 통계에서 창의 일부(수백 건)가 창 전체 저장 길이의 절반을 차지했다. 이 증가는 쓰기 분포에 의존하며 소스의 불변식이 아니다.
4. **재빌드가 새 인덱스를 완성한 뒤에 교체한다.** 교체 시점에 옛 인덱스와 새 인덱스가 함께 산다. 이 두 배는 설계상 불가피하다. 해제된 메모리는 glibc 아레나에 남아 RSS가 내려오지 않는다.
5. **쓰기마다 재빌드가 이어진다.** 쓰기는 문서 수와 최신 시각을 바꾸고, 지문이 바뀌면 워커가 전체 창을 다시 읽고 다시 토큰화한다. 재빌드가 디바운스(1.5초)보다 오래 걸리므로 쓰기가 계속되는 동안 워커가 쉬지 않는다.

## 수정

### 1. 워커 지역 참조 해제

`_rebuild_loop`의 `try` 블록에 `finally`를 붙여 `state`, `candidate`, `observation`, `probe`를 회차마다 `None`으로 되돌린다. 성공, 폐기, 변화 없음(`continue`), 예외 어느 경로로 나가도 해제된다. 이 항목은 동작을 바꾸지 않는다. 검색이 잡은 상태 참조는 검색이 끝나면 풀린다.

### 2. 토큰 문자열 공유

`BM25Index.build`가 빌드 중 어휘 사전(`dict[str, str]`)을 둔다. 토큰 리스트의 항목은 사전이 가진 단일 `str` 객체를 가리킨다. `_tokens`는 여전히 `list[list[str]]`이고 점수 계산과 검색 결과는 변하지 않는다. 토큰당 비용이 객체 하나에서 리스트 슬롯 하나로 줄어든다.

### 3. 인덱스 입력의 크기 상한

환경변수 두 개를 둔다. 길이의 단위는 스토어가 `properties`를 저장한 문자열의 길이다. SQLite 스토어는 `ensure_ascii=True`로 직렬화하므로 한글이 글자당 6자로 센다. PostgreSQL JSONB는 이스케이프하지 않는다. 따라서 이 값은 백엔드마다 의미가 다른 크기 근사치다. 파이썬 대체 경로는 `json.dumps(properties, ensure_ascii=True, default=str)`의 길이를 쓴다. 이 길이는 SQLite 저장 형식과 같다. `default=str`은 MongoDB가 BSON으로 돌려주는 `datetime` 같은 JSON 밖의 값도 크기를 셀 수 있게 한다. 직렬화가 그래도 실패하면(순환 참조 등) `repr`의 길이를 쓴다. 크기 계산은 빌드를 실패시키지 않는다.

- `OPENCRAB_BM25_MAX_NODE_CHARS`(기본 65536): 이 값을 넘는 노드는 BM25 인덱스에 넣지 않는다. `0` 이하이면 이 상한을 끈다.
- `OPENCRAB_BM25_CHAR_BUDGET`(기본 80_000_000): 인덱스에 들어가는 노드의 길이 합의 상한이다. `0` 이하이면 끈다.

창은 세 단계를 이 순서로 거친다. 계약은 SQL 경로와 파이썬 대체 경로가 같다. 1단계의 순서는 스토어의 `list_nodes` 계약을 따른다. `_SqlDocStoreBase`는 최신순을 보장한다. `MongoStore.list_nodes`와 `LocalDocStore.list_nodes`는 순서를 보장하지 않으며 이 변경은 그 기존 동작을 고치지 않는다. 대체 경로는 스토어가 돌려준 순서를 그대로 쓰고, "최신순"은 순서를 보장하는 스토어에서만 성립한다.

1. 최신순(`updated_at DESC, space, node_id`) 상위 `_BM25_NODE_LIMIT`개를 고른다.
2. 그중 길이가 크기 상한을 넘는 노드를 뺀다. 빈자리는 더 오래된 노드로 채우지 않는다.
3. 남은 노드를 최신순으로 누적한다. 직전 누적이 예산보다 작은 노드까지 담는다. 누적이 예산에 닿거나 넘긴 노드의 뒤는 담지 않는다. 마지막 노드 하나가 예산을 넘길 수 있다.

구현은 두 부분이다.

- `_SqlDocStoreBase`에 `list_nodes_within_budget(limit, max_chars, max_node_chars)`를 더한다. 안쪽 질의가 1단계를 하고 길이를 `LENGTH(CAST(properties AS TEXT))`로 계산하며, 2단계 거르기 뒤에 윈도 함수로 누적 길이를 구해 3단계에서 자른다. 윈도 함수는 SQLite 3.25 이상과 PostgreSQL에 있다. 담길 행만 파이썬으로 넘어온다.
- `_observe`는 이 메서드가 있고 리스트를 돌려주면 그것을 쓴다. 없거나 리스트가 아니거나 예외를 내면(예: 윈도 함수가 없는 SQLite 3.25 미만) `list_nodes(limit)`로 읽고 `trim_to_budget`(`bm25.py`)으로 같은 2단계와 3단계를 파이썬에서 적용한다.

지문 계약: 네이티브 지문이 없는 스토어(legacy)는 지금처럼 `list_nodes(limit)` 원본 목록으로 지문을 계산한다. 이 변경은 지문을 자른 목록에서 계산하지 않는다. `_bm25_probe_fingerprint`의 legacy 경로가 같은 원본 목록으로 지문을 계산하므로 두 지문이 일치한다. 자르기는 지문 계산 뒤에 인덱스 입력에만 적용한다. 네이티브 지문 스토어는 전체 테이블 지문을 쓰므로 영향이 없다.

커버리지 경고 계약: 크기 상한과 예산에 걸리면 `indexed_rows < total_rows`가 되어 기존 `BM25 coverage partial rows` 경고가 나온다. 건수 상한에서 이미 나오던 경고다. legacy 스토어는 `total_rows`가 `None`이어서 `BM25 coverage total unknown`이 그대로 나온다.

검색 누락 판정: 크기 상한을 넘는 노드는 BM25 검색 결과에서 빠진다. 이 노드의 다른 검색 경로를 이 변경은 바꾸지 않는다. 그 경로가 항상 있다고 보장하지 않는다. 벡터 색인은 노드 텍스트의 앞 4000자를 쓰고, 선택 사항이며 쓰기 실패 시 비어 있을 수 있다. 문서 FTS는 `doc_sources`를 검색하므로 노드만 쓴 경우 해당하지 않는다. 이 누락을 막으려면 크기 상한을 끄거나(`0`) 높인다. 기본값은 라이브 창에서 소수 노드가 절반의 바이트를 차지하는 관측에 맞춘 것이며, 값의 근거 수치는 PR 본문과 커밋 메시지에 둔다.

### 4. 재빌드 휴지

휴지 기한은 `_Bm25CacheWorker`가 단조 시계(`time.monotonic()`) 값 `_next_build_at`으로 소유한다. 읽기와 쓰기는 기존 `_lock` 아래에서 한다.

- 기한을 쓰는 곳: 인덱스 관측(`_observe`)이나 빌드(`_make_state`)를 한 모든 경로가 끝날 때다. 백그라운드 회차의 게시, 폐기, 변화 없음 판정, 관측이나 빌드가 예외로 끝난 경우, 그리고 `ensure_built`의 동기 빌드가 포함된다. 예외 경로는 `except` 안에서 같은 `_lock` 아래 기한을 쓴다. 이 경로는 게시된 상태가 있는 백그라운드 재빌드에만 해당한다. 쓰기가 이어지는 중에 `MemoryError` 같은 실패가 나도 워커가 연속 재시도하지 않게 한다. 게시된 상태가 아직 없는 첫 빌드의 실패는 이 변경 전과 같이 기한을 쓰지 않는다(범위 밖 절 참고). 기한은 `끝난 시각 + 2 × (그 작업에 걸린 시간)`이다. 검색 스레드가 부른 `ensure_built`도 같은 필드를 갱신하므로 첫 빌드 중 쓰기가 들어오면 첫 백그라운드 재빌드는 첫 빌드 길이의 두 배를 기다린다.
- 기한을 읽는 곳: `_rebuild_loop`가 `_wake`를 소비하고 디바운스를 기다린 뒤다. 읽기는 반복이다. 매번 `_lock` 아래에서 `state`, `_next_build_at`, `_epoch`를 한 번에 스냅샷한다. `state`가 있고 기한이 남아 있으면 `_lock`을 풀고 `_stop.wait(남은 시간)`으로 기다린 뒤 스냅샷부터 다시 한다. 기한이 지났거나 `state`가 없으면 반복을 끝내고 그 스냅샷으로 회차를 진행한다. `state`가 없으면 보호할 인덱스가 없고, 기한은 `state`를 게시한 작업이 쓰므로 `state`가 없을 때 기한은 쓰이지 않았다. 대기 중에 검색 스레드의 `ensure_built`가 상태를 게시하고 기한을 새로 설정하면 다음 스냅샷이 그것을 본다. 종료 신호는 대기를 즉시 깨우며 대기마다 `_stop.is_set()`를 확인한다. `_lock` 안에서는 기다리지 않는다.
- 검색 스레드의 동기 빌드(`ensure_built`)는 기한을 기다리지 않는다. 질의에 답해야 하기 때문이다. - 첫 빌드 경로: `_rebuild_loop`가 `state is None`이라 `ensure_built`를 부른 회차는 거기서 끝난다. 워커는 `_wake`를 다시 설정하고 회차 맨 앞으로 돌아간다(`continue`). 스냅샷이 `state is None`이었던 회차에서는 지문 검사와 `_make_state`로 이어지지 않는다. 다음 회차가 위 기한 대기를 거친다. 검색 스레드가 첫 빌드를 맡고 워커가 `_cold_build_lock`에서 기다렸다가 풀려난 경우도 같은 경로를 탄다. 추가 회차는 지문을 비교해 변화가 없으면 빌드 없이 끝난다.
- 대기 중 `invalidate`와 `mark_stale`은 `_wake`, `_epoch`, `dirty`만 건드린다. 이 호출은 기한을 바꾸지 않는다. 대기 중 설정된 `_wake`는 다음 회차를 한 번 더 깨운다. 그 회차는 지문을 비교해 변화가 없으면 빌드 없이 끝난다.
- 쓰기 폭주 중에도 워커의 빌드 점유율은 3분의 1을 넘지 않는다. 빌드가 밀리초인 소규모 코퍼스와 시험에서는 휴지가 보이지 않는다.

휴지 중 상태: 옛 `state`가 유지되고 검색이 그것을 즉시 서빙한다. 최신 쓰기는 휴지가 끝난 뒤 첫 관측이 지문 비교로 흡수한다. 휴지 중에 온 `invalidate`는 `_wake`를 다시 설정하므로 쓰기가 영구히 누락되지 않는다. 게시 직후 `dirty=False`이고 휴지 중 쓰기가 오면 `dirty=True`로 바뀐다.

### 5. 재빌드 뒤 반환

게시와 지역 참조 해제(수정 1) 뒤 워커가 `malloc_trim(0)`을 호출해 아레나의 빈 메모리를 운영체제에 돌려준다. `libc.malloc_trim`이 없는 환경에서는 호출을 건너뛴다. 이 호출은 이미 해제된 메모리만 돌려준다. 살아 있는 객체는 수정 1이 해제한다. 둘의 효과는 측정에서 나눠 확인한다. 호출은 `malloc_trim`의 인자(`size_t`)와 반환(`int`) 형식을 명시한다. 관측이나 빌드를 한 회차는 참조 해제와 반환이 끝난 뒤 `DEBUG` 로그 한 줄("BM25 worker round finished")을 남긴다. 측정 관찰자가 이 줄을 표본 기준으로 쓴다.

## 호출자와 형제 경로

- `BM25Index.build`의 호출자: `_make_state`(서버), `packs reindex-bm25` CLI. 둘 다 어휘 공유를 받는다. CLI는 `list_nodes(limit=200000)` 결과를 그대로 넘기며 크기 상한과 예산을 받지 않는다. 일회성 프로세스이고 서버 상주 메모리와 무관하다. 후속 후보로 남긴다.
- `list_nodes`는 그대로 둔다. 다른 호출자의 계약이 변하지 않는다.
- `_bm25_probe_fingerprint`의 legacy 경로는 건수 상한만 받는 전체 목록을 읽는다. 이 변경은 그 경로를 건드리지 않는다. 상주 서버가 쓰는 SQL 계열 스토어에는 네이티브 지문이 있어 이 경로를 타지 않는다. 후속 후보로 남긴다.
- 쓰기 핸들러의 `invalidate_bm25_cache()` 호출은 그대로다.
- `ensure_built`(첫 질의의 동기 빌드)의 지역 변수는 함수가 끝나면 풀린다. 수정 1은 `_rebuild_loop`만 바꾼다.
- 프로세스가 도중에 죽으면 캐시와 워커 스레드가 함께 사라진다. 영속 자원은 없고 다음 프로세스의 첫 질의나 첫 쓰기 뒤 깨움이 저장된 문서로 인덱스를 다시 만든다.

## SOLID 판정

단일 책임: 예산 규칙은 스토어 메서드와 순수 함수 `trim_to_budget`에 둔다. 워커는 두 경로 중 하나를 고르고 휴지 기한을 관리한다. 개방 폐쇄: 새 스토어 메서드는 선택 능력이며 없으면 대체 경로를 쓴다. 두 경로의 계약은 위 3단계로 같고 시험이 같은 입력의 결과 동일을 확인한다. 인터페이스 분리: 워커는 `list_nodes_within_budget`만 본다. 의존 역전: 워커는 구체 스토어 클래스를 만들지 않는다. 기존 코드의 위반은 건드리지 않는다.

## 시험 전략

- 지역 참조: 게시와 폐기 뒤에 워커 스레드가 유휴일 때 이전 인덱스와 폐기된 후보가 약한 참조로 살아 있지 않다. 현재 서비스 중인 인덱스는 폐기와 변화 없음 뒤에도 정상적으로 산다.
- 어휘 공유: 두 문서에 같은 토큰이 있을 때 `_tokens`의 두 항목이 같은 객체이다. 점수는 인덱스 내부를 쓰지 않는 독립 기준과 같다. 기준은 `tokenize()`와 `_node_text()`만으로 문서 빈도, 평균 길이, IDF, 점수를 공유 없이 따로 계산한다. 공유 처리에서 토큰을 빠뜨리면 기준과 달라진다.
- 크기 상한과 예산: 큰 노드와 작은 노드를 섞은 스토어에서 `list_nodes_within_budget`이 창 규칙 3단계를 따른다. 최신순 `[큰 노드, A, B]`와 `limit=2`에서 `[A]`를 돌려주고, 파이썬 대체 경로가 같은 결과를 낸다. 마지막 노드 하나만 예산을 넘긴다. 상한 `0` 이하는 거르지 않는다. 경계 값(길이가 상한과 같은 노드)을 두 경로에서 포함한다. 윈도 질의가 예외를 내면 파이썬 경로로 대신한다.
- 크기 계산의 견고성: `datetime`이나 직렬화할 수 없는 값을 가진 노드가 있어도 `node_size`가 예외를 내지 않고 legacy 경로의 빌드가 성공한다.
- 지문: legacy 스토어에서 자른 인덱스의 지문이 `_bm25_probe_fingerprint`와 같아 불필요한 재빌드가 연속으로 일어나지 않는다.
- 커버리지: 상한에 걸린 인덱스는 `indexed_rows < total_rows`이고 partial 경고가 나온다.
- 휴지: 시험은 순서를 사건으로 강제하고(잠금 획득 시도를 기록하는 계측 잠금, 이벤트), 시간은 휴지 하한과 종료 상한을 확인하는 데만 쓴다. 시간은 실제 시계와 짧은 지연(빌드 0.15초, 허용 오차는 지연의 3분의 1 미만)이다. 기한 이전에는 다음 빌드가 시작하지 않고 기한이 지나면 시작한다. 다음 경우를 검증한다. 첫째, 워커가 첫 빌드를 맡고 그 빌드 중 쓰기가 들어온다. 둘째, 워커가 대기하는 동안 검색 스레드가 첫 빌드를 끝내고 그 사이 쓰기가 들어온다. 셋째, 검색 스레드가 `_cold_build_lock`을 쥐고 있어 워커가 `ensure_built`에서 막힌 채 검색 스레드가 상태와 기한을 게시한다. 넷째, 느린 빌드나 폐기된 빌드 뒤에 쓰기가 이어진다. 다섯째, 게시된 상태가 있을 때 관측이나 빌드가 예외로 끝난 뒤에도 다음 시도가 기한 이전에 시작하지 않는다. 반복 `mark_stale`은 기한을 바꾸지 않는다. 휴지가 끝난 뒤 마지막 쓰기가 검색 결과에 나타난다. 종료 신호는 긴 휴지(기한을 먼 미래로 둔다)를 즉시 끝낸다.
- 시간축 측정: 위 측정 절차대로 격리 인스턴스에 쓰기 부하를 걸어 수정 전과 수정 후 RSS를 같은 조건으로 잰다.

## 받아들임 기준

- 측정 절차: 보정 실행과 판정 실행을 나눈다. 판정 실행의 매개변수와 합격 허용치를 실행 전에 PR 본문에 적는 사전 등록 기록으로 고정하고, 하네스 결함이 나오면 정정 기록을 덧붙여 판정 실행을 다시 한다. 정정 뒤에도 구간과 허용치는 바꾸지 않는다. 정정 전 실행은 합격 근거에서 뺀다. 사전 등록 조건을 충족하지 못한 실행이 있으면 그 사실을 PR 본문에 적는다. 수정 전 코드와 수정 후 코드를 같은 매개변수로 각각 실행한다. 제한 값은 서버 프로세스 환경변수로 전달한다(`os.getenv`가 읽는다). 환경 파일에 쓴 값은 이 변수들에 닿지 않는다.
- 하네스 계약: 재빌드 완료 직후 RSS는 서버 로그를 따라가는 관찰자가 기록한다. 기준 줄은 워커 회차의 마지막 줄(참조 해제와 메모리 반환이 끝난 뒤 `DEBUG`로 한 줄 남기는 "BM25 worker round finished")이다. 관찰자는 그 줄이 나타난 즉시 서버 프로세스의 RSS를 읽어 시각과 함께 기록한다. 게시 줄이나 폐기 줄은 참조 해제와 반환보다 앞서므로 기준으로 쓰지 않는다. 회차마다 정확히 한 줄이 남고 완료한 재빌드(게시, 폐기, 변화 없음 관측)를 센다. 쓰기 건수로 시각을 짐작하지 않는다. 부하 생성기는 RSS를 읽은 뒤 시각을 기록하고 종료 표본도 최대값에 포함한다. 부하가 끝나면 마지막 쓰기에만 있는 고유 토큰을 `ontology_query`로 조회해 그 쓰기가 BM25 경로로 검색되는지 확인한다.
- 판정 구간: 시작 후 150초부터 끝까지다. 이 구간에 완료한 재빌드(게시와 폐기)가 최소 세 번 들어 있어야 한다. 줄이 모자라면 불합격이다.
- 합격 조건: 판정 구간에서 RSS를 시간에 대해 선형 회귀한 기울기에 구간 길이를 곱한 값이 구간 평균 RSS의 5퍼센트 이하다. 재빌드 완료 직후 RSS 계열은 판정 구간을 시간으로 3등분해 첫 3분의 1과 마지막 3분의 1에 각각 표본이 두 개 이상 있어야 하고(모자라면 불합격), 두 중앙값의 차이가 첫 3분의 1 중앙값의 5퍼센트 이하다. 수정 후 최대 RSS는 수정 전 같은 매개변수 실행의 최대 RSS보다 낮다. 수정 전 실행은 같은 판정 구간에서 회귀 조건을 어긴다. 마지막 쓰기의 검색 조회가 성공한다.
- 기존 BM25 시험이 전량 통과한다.
- 새 시험이 원인 경로(지역 참조, 어휘 공유, 크기 상한과 예산, 지문, 휴지)마다 있고 구현을 되돌리면 실패한다.

## 범위 밖

- 문서(`properties`) 본문을 인덱스가 계속 들고 있는 구조. 결과 문서를 요청 시점에 스토어에서 읽는 구조로 바꾸면 메모리가 더 준다. 구조 변경이라 후속으로 둔다.
- 쓰기 전용 인스턴스가 질의 전에 인덱스를 미리 빌드하는 동작(#398 설계의 첫 wake 규칙).
- CLI `packs reindex-bm25`와 legacy 지문 경로의 전체 목록 읽기.
- 게시된 상태가 없는 첫 빌드의 실패 재시도. 쓰기가 올 때마다 워커가 다시 시도하는 동작은 이 변경 전과 같다. 이 변경은 그것을 새로 도달 가능하게 만들지 않는다.
- PostgreSQL 스토어와 파이썬 대체 경로 사이의 길이 단위 차이(한글 이스케이프). 상한 경계 근처 노드의 선택이 백엔드마다 달라질 수 있다. 후속 후보로 남긴다.
- 로컬 GGUF 폴백과 ANN 캐시.
